# Update Log — 2026-04-25

## Changes

### Phase 2 — Multi-Input, Multi-Device, Multi-Player

Implemented Phase 2 on top of the working Phase 1 codebase. This is a breaking change
across the MQTT topic schema, payload format, device registry, and proto contract.

**New proto (`Proto/game_controller_v2.proto`):**
- Package renamed to `game_controller.v2`, namespace to `GameController.V2`
- Added `SendInputBatch` RPC and `InputBatchRequest` message
- New fields: `input_name`, `input_type`, `value`, `sequence_number`

**New `Models/DeviceRegistryConfig.cs`:**
Typed config model for the nested registry hierarchy (`players → devices → inputs`).

**Updated `Services/DeviceRegistryService.cs`:**
- Loads nested config instead of flat `Dictionary<string, string>`
- `ResolveInput(deviceId, inputName)` returns `InputRegistryEntry` with `PlayerId`, `InputType`, `MinRaw`, `MaxRaw`
- Resolution priority: input-level `playerId` → device `defaultPlayerId` → null (drop)
- `NormalizeValue(entry, raw)` clamps knob/ADC values to `0.0–1.0` using `minRaw`/`maxRaw`

**New `Services/InputBufferService.cs`:**
- Sits between MQTT and Unity; transparent at `BufferWindowMs = 0`
- When `BufferWindowMs > 0`: accumulates events via `PeriodicTimer` and flushes as a single `SendInputBatch` call
- Per-key token bucket rate limiter (`MaxEventsPerSecond`, default 60) prevents sensor flood
- Rate limiter key is `deviceId:inputName`

**Updated `Services/MqttSubscriberService.cs`:**
- New wildcard subscription: `game/devices/+/input/+`
- Routes through `InputBufferService` instead of calling `UnityRelayService` directly

**Updated `Services/UnityRelayService.cs`:**
- Uses v2 generated stub
- Replaced `SendButtonEvent` with `SendInputBatch(IEnumerable<InputEventRequest>)`

**Updated `appsettings.json`:**
- `DeviceRegistry` is now a nested `players/devices/inputs` structure
- Added `IoTGame` section with `BufferWindowMs` and `MaxEventsPerSecond`

### gRPC SSL Error Fix

**Error (from IDE):**
```
Grpc.Core.RpcException: Status(StatusCode="Internal",
  Detail="Error starting gRPC call. HttpRequestException: The SSL connection could not
  be established. AuthenticationException: Cannot determine the frame size or a
  corrupted frame was received.")
```

**Root Cause:**
`Unity:GrpcEndpoint` was `https://localhost:9090` but the local Unity dev server
uses plain HTTP/2 (no TLS cert). The SSL handshake received plain HTTP/2 bytes and
crashed.

**Fix (`Services/UnityRelayService.cs` + `appsettings.json`):**
- Changed default endpoint to `http://localhost:9090`
- When endpoint starts with `http://`, sets `Http2UnencryptedSupport` switch and
  passes a plain `HttpClientHandler` to `GrpcChannelOptions`

```csharp
if (endpoint.StartsWith("http://"))
{
    channelOptions.HttpHandler = new HttpClientHandler();
    AppContext.SetSwitch("System.Net.Http.SocketsHttpHandler.Http2UnencryptedSupport", true);
}
```

**Rule:** Use `http://` for local Unity dev server. Switch to `https://` in production
when Unity is behind a reverse proxy with a valid cert.

### Phase 2.1 — Protocol Fix: Separate Physical Slot Identity from Semantic Input Name

**Problem with Phase 2:**
`inputName` served two purposes — physical slot identification (MQTT routing key) and
semantic game label (what Unity sees). This made it impossible to have two physical
buttons on the same device both named `"jump"` for different players. The workaround
of `"p1-jump"` / `"p2-jump"` smuggled player identity into the name.

**Fix — three separate concerns, three separate fields:**

| Field | Meaning | Owned by |
|---|---|---|
| `slotId` | Physical hardware slot identifier | Firmware + MQTT topic |
| `inputName` | Semantic game label (`"jump"`, `"speed"`) | ASP.NET registry only |
| `playerId` | Player this slot belongs to | ASP.NET registry only |

**MQTT topic changed (breaking):**
```
game/devices/{deviceId}/input/{inputName}   ← Phase 2 (removed)
game/devices/{deviceId}/slot/{slotId}       ← Phase 2.1
```

**Payload change:** `inputName` removed from firmware payload. The server resolves it
from the registry.

**Registry schema change:** Keys under `"inputs"` are now `slotId` values (physical).
Each entry now has an `inputName` field (semantic):

```json
"btn1": { "type": "button", "inputName": "jump" },
"btn2": { "type": "button", "inputName": "jump", "playerId": "player-2" }
```

Both `btn1` and `btn2` resolve to `inputName: "jump"` for different players — the
collision that was impossible in Phase 2.

**Files changed:**
- `Models/DeviceRegistryConfig.cs` — added `InputName` to `InputConfig`; `InputRegistryEntry` is now a record with `InputName`
- `Models/InputEvent.cs` — redesigned; now carries fully resolved fields (`PlayerId`, `SlotId`, `InputName`) built after registry lookup
- `Services/DeviceRegistryService.cs` — `ResolveInput(deviceId, slotId)` now returns `InputName` in the entry
- `Services/MqttSubscriberService.cs` — subscribes to `game/devices/+/slot/+`; parses `slotId` from topic; builds resolved `InputEvent` after registry lookup
- `Services/InputBufferService.cs` — `EnqueueAsync(InputEvent)` simplified; rate limiter key is now `deviceId:slotId`
- `appsettings.json` — registry updated to slot-keyed format with `inputName` fields

**Proto unchanged** — Unity already receives `inputName` (semantic) and `playerId`.
`slotId` is intentionally excluded; Unity has no use for physical device topology.
