### Phase 3.1 — Auxiliary Field for Multi-Output Sensors

**Problem:**
DHT11 produces two readings per poll (temperature + humidity) but the protocol had
no place for a second value from a single slot. Phase 3 silently discarded humidity.

**Fix — `auxiliary` map added to all three proto messages:**

```proto
map<string, float> auxiliary = 9;  // InputEventRequest
map<string, float> auxiliary = 4;  // EnvironmentEventRequest
map<string, float> auxiliary = 4;  // AdminCommandRequest
```

Fully additive — existing receivers that ignore unknown fields are unaffected.

**Registry — `auxiliaryKeys` added to `InputConfig`:**
Maps firmware payload keys to `envKey` values forwarded to Unity:

```json
"dht11": {
  "envKey": "temperature",
  "auxiliaryKeys": { "humidity": "humidity" }
}
```

**Routing logic (`MqttSubscriberService.HandleEnvironmentEvent`):**
After forwarding the primary value, loops over `raw.Auxiliary`. Each entry is looked
up in `entry.AuxiliaryKeys`; if found, a second `SendEnvironmentEvent` call is made
with the resolved `envKey`. Unknown auxiliary keys are dropped at `Debug` log level only.

**`InputEvent.cs`:** Added `Dictionary<string, float> Auxiliary` parameter.

**`InputBufferService.cs`:** Copies `Auxiliary` entries into `InputEventRequest` when present.

### Phase 3.2 — Swap Temperature and Humidity Effects

**Problem:**
Hardware testing revealed that temperature changes very slowly (10–30 s) while
humidity responds within 2–3 s. The original effect assignment was backwards for
a real-time demo — temperature was driving spawn rate (fast effect) and humidity
was unused.

**Corrected assignment:**

| Sensor | Phase 3 (wrong) | Phase 3.2 (correct) |
|---|---|---|
| Temperature | spawn rate | gravity strength |
| Humidity | nothing | spawn rate |

**Fix — registry `envKey` rename only (`appsettings.json`):**

```json
"dht11": {
  "envKey": "gravity",
  "auxiliaryKeys": { "humidity": "spawn_rate" }
}
```

No proto change. No firmware change. No code change. Unity receives self-describing
semantic keys (`"gravity"`, `"spawn_rate"`) and never needs to know the physical sensor.

## Key Design Decisions

### SessionId in MQTT payload (Phase 4)
Events now require a `sessionId` field in the MQTT payload. This allows the server to route to the correct Unity instance and look up per-session slot mappings. Events without `sessionId` are dropped with a warning.

### UnityRelayService as channel pool
Instead of a single channel, the relay now maintains a `ConcurrentDictionary<endpoint, ChannelEntry>`. This supports multiple concurrent game sessions each pointing to different Unity servers.

### Shared secret on every gRPC call
If `IoTGame:SharedSecret` is configured, it is sent as `x-iotgame-secret` metadata on every outgoing RPC. Unity validates it server-side.

**Error (observed at runtime):**
```
fail: ATITInfraNode.Services.UnityRelayService[0]
      gRPC SendEnvironmentEvent failed
      Grpc.Core.RpcException: Status(StatusCode="Unimplemented", Detail="")
        at ATITInfraNode.Services.UnityRelayService.SendEnvironmentEvent(EnvironmentEvent evt)
```

**Root Cause:**
This server successfully called Unity over gRPC. The error originates on the **Unity
side** — Unity's gRPC server received the call but has no handler registered for
`SendEnvironmentEvent`. Unity has not yet regenerated stubs from the updated proto
and/or has not implemented the new RPC on its `GameControllerService` class.

**Status:** Not fixed — Unity-side work required (see "What to Continue" below).
